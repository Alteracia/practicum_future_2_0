# Проектирование целевой архитектуры
![C4 one Year.drawio.png](C4%20one%20Year.drawio.png)

## Как предложенная схема поддерживает ключевые сценарии:
1. Витрина данных как отдельный продукт. «Портал самообслуживания» — самостоятельный контейнер: каталог витрин, конструктор отчётов, экспорт, доступ по ролям. В него заходят и аналитики головного офиса, и бизнес‑пользователи доменов (клиника, финтех, партнёры) — портал не принадлежит ни одному домену.
2. Быстрая подготовка отчётности. Отчёты строятся не по сырым таблицам DWH с трансформациями «на лету», а по курированному слою lakehouse: портал и BI обращаются к семантическому слою Dremio поверх Iceberg — часы превращаются в минуты. Кастомная логика, которая раньше жила в BI, вынесена в витрины.
3. Независимое развитие финтеха и ИИ. У каждого домена своя БД и своя логика; наружу — только data‑продукт. Финтех может релизиться хоть каждый день, не согласовывая изменения с ИИ‑доменом или клиниками.
4. Масштабирование для новых бизнесов. Фармкомпания и производитель электроники подключаются как внешние домены‑партнёры по тому же контракту data‑продукта, не трогая DWH и не требуя новой центральной логики.
5. Целостная картина по KPI при автономности доменов. Каталог и портал агрегируют data‑продукты всех доменов в общие показатели, даже когда домены развиваются независимо.
6. Закрыто требование: медкарты, истории болезни и результаты исследований остаются в домене «Клиники» / хранилище ИИ‑сервисов и не публикуются как data‑продукт в витрину.
7. Легаси не выключается «одним днём». DWH (MS SQL Server 2008) и ESB (Apache Camel) остаются на схеме в контуре «Легаси (план вывода из эксплуатации)»: DWH отдаёт историю в lakehouse через CDC + backfill, операторский PowerBuilder‑интерфейс временно продолжает работать по старому пути через ESB. Это strangler‑переход: домены переезжают по одному, легаси отключается по мере переноса витрин, что и допускает бизнес‑цель на горизонте года.
