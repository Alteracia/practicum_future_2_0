# Обоснование конфигурации

## Основание и назначение

В изученном PDF «Управление облачной инфраструктурой и Infrastructure as Code — Яндекс Практикум» описаны декларативный и императивный подходы, цикл init → plan → apply, назначение state, провайдеров и пример VM/disk/network для Yandex Cloud (страницы 2–10). Задание 4 из Tasks.md требует реализовать инфраструктурный проект, схему и доказательство успешного apply.

Выбран Yandex Cloud, поскольку он используется в практическом примере материала. Это проектное решение для учебной работы; оно не означает согласованного выбора провайдера для всей компании.

## Ресурсы

| Компонент | Конфигурация | Почему |
|---|---|---|
| VPC | Отдельная сеть `future20-task4-network` | Sandbox не подключается к сетям клиники, банка и реальным данным |
| Subnet | `10.40.10.0/24`, зона `ru-central1-a` | Простая частная адресация с запасом для учебных узлов; подсеть, диск и ВМ находятся в одной зоне |
| Security group | Входящий TCP/22 только от `admin_cidr /32`; остальное входящее запрещено отсутствием разрешающих правил | SSH доступен с одного заданного IPv4; порты БД, BI и приложений не публикуются |
| Исходящий трафик | ANY в `0.0.0.0/0` | Для учебного стенда допускаются DNS, NTP, обновления ОС и пакеты. Для production требуется пересмотреть egress по назначениям; это не строгая фильтрация исходящего трафика |
| VM | `standard-v3`, 2 vCPU, 4 GiB RAM, 100% CPU, непрерываемая | Достаточный начальный ресурс для ОС и одного небольшого тестового сервиса; нет ложного обещания разместить Dremio, Airflow и всё хранилище на 4 GiB |
| Boot Disk | Отдельный `network-ssd`, 30 GiB | ОС, пакеты, журналы и небольшие синтетические наборы; SSD выбран для отзывчивости. Объём больше 15 GiB из урока даёт запас для обновлений |
| Образ ОС | Семейство Ubuntu 22.04 LTS; возможность задать immutable image ID | Соответствует примеру урока. Выбранный ID выводится для фиксации; family без фиксации не гарантирует побитово одинаковую ОС при новом развёртывании |
| NIC/NAT | `nat = true`, динамический публичный IPv4 | Прямой SSH для одной лабораторной ВМ и выход в интернет без отдельного NAT gateway/бастиона |
| OS-пользователь | `ubuntu`, публичный Ed25519 ключ, парольный SSH и root-вход отключены через cloud-init | Автоматический воспроизводимый доступ без приватного ключа в Terraform |

2 vCPU / 4 GiB и 30 GiB — стартовые учебные значения, а не результат нагрузочных испытаний. RAM/CPU изменяются переменными в допустимом диапазоне; рост диска требует проверки плана, уменьшение используемого диска не является безопасным способом экономии.

## NAT и сетевой доступ

Публичный IPv4 сопоставляется внутреннему адресу NIC средствами Yandex Cloud. `nat = true` не создаёт отдельную NAT-VM и не включает маршрутизатор внутри Ubuntu. Security group ограничивает входящие подключения независимо от наличия публичного IP.

Для VM с публичным IP отдельная таблица маршрутов к NAT gateway не требуется. В промышленной архитектуре следует рассмотреть приватные ВМ, VPN/бастион и исходящий NAT gateway: это другой набор ресурсов и отдельная стоимость. Для одной лабораторной машины такой набор избыточен.

Описание поведения адресации и NAT: [документация Yandex Compute](https://yandex.cloud/ru/docs/terraform/resources/compute_instance). Доступ определяется [правилами security group](https://yandex.cloud/ru/docs/terraform/resources/vpc_security_group).

## Что автоматизировано, а что выполняется вручную

| Объект / действие | Способ | Где описано |
|---|---|---|
| VPC, subnet, security group, disk, VM и NIC/NAT | Terraform | Пять resource-блоков в main.tf |
| Выбор существующего образа | Terraform data source | `data.yandex_compute_image.ubuntu` либо входной image_id |
| Пользователь и параметры SSH | Cloud-init через metadata, сформированную Terraform | `metadata.user-data` |
| Облако, биллинг, каталог, разрешения оператора | Администратор до запуска | Предусловия README; Terraform их не создаёт |
| Локальная авторизация, SSH-ключ, review плана | Оператор | Вне state и репозитория для секретных частей |
| Установка приложения, его настройки и данные | Отдельный ручной шаг после IaaS | Не входит в данный Terraform-проект |
| Скриншот реального apply и SSH-приёмка | Оператор после успешного развёртывания | evidence/apply-success.png; файл ещё не создан |

Схема не объявляет созданными managed DB, object storage, lakehouse, резервную площадку или IAM-роли. Они не нужны для этого минимального задания и потребовали бы отдельной конфигурации.

## Почему декларативный Terraform

HCL описывает нужное состояние; ссылки `network_id`, `subnet_id`, `disk_id` и `security_group_ids` формируют граф зависимостей. Terraform сам создаёт сеть до подсети, диск до ВМ и подключает подготовленные ресурсы. Ручная последовательность команд создания каждого ресурса не нужна.

Файлы и lock-файл позволяют повторить конфигурацию, а plan делает изменение обозримым до выполнения. Переменные позволяют адаптировать зону, размер ВМ и диск; отдельные каталоги и state разграничивают окружения. Это снижает объём ручных действий при подключении новых доменных стендов из Task3.

IaC не гарантирует отсутствия ошибок и не восстанавливает данные автоматически. Возврат Git-коммита должен сопровождаться новым plan: обратное изменение может требовать замены ВМ или диска. Backup, восстановление БД и управление схемами приложений остаются отдельными задачами.

## Стоимость, воспроизводимость и ограничения

Тарифицируемые части — вычисления, SSD и публичный IP; дополнительно учитывается исходящий трафик. Фиксированная сумма не приводится без выбранного платёжного аккаунта и длительности работы. Перед apply оператор проверяет стоимость через [калькулятор Yandex Cloud](https://yandex.cloud/ru/prices) и согласованный лимит. Размеры ограничены валидацией переменных, ресурсы маркируются labels для поиска.

Учебный стенд работает в одной зоне: это единая область отказа, он не выполняет требования годовой production-архитектуры по георезервированию. На нём нет данных пациентов и клиентов банка. Переход в production требует результатов обследования Task3, разделения контуров, IAM, защищённого state, резервирования, восстановления, мониторинга и нагрузочных измерений.

Провайдер и контрольные суммы закреплены в `.terraform.lock.hcl`. Токены, приватные ключи, state, plan и локальные параметры исключены из Git. Конкретный ID образа стоит зафиксировать после первого реального plan; обновление образа затем выполняется осознанным изменением.

Официальные справочники, использованные при проверке: [начало работы с Terraform в Yandex Cloud](https://yandex.cloud/ru/docs/tutorials/infrastructure-management/terraform-quickstart), [ресурс VM](https://yandex.cloud/ru/docs/terraform/resources/compute_instance), [платформы Compute](https://yandex.cloud/ru/docs/compute/concepts/vm-platforms), [data source образа](https://yandex.cloud/ru/docs/terraform/data-sources/compute_image). HCL дополнительно проверен схемой установленного провайдера 0.161.0.
